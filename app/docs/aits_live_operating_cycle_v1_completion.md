# AITS Live Operating Cycle v1 Completion

## 1. Scope

Live Operating Cycle v1 connects market and account facts to AI decisions, guarded execution, post-order state refresh, replanning, training evidence, and user-visible reasons. BASIC remains the fact and calculation provider. AI supplies decisions; Router, RiskGuard, LivePreflight, and the existing execution stack retain their boundaries.

## 2. Active Path

1. ON activates the runtime contract and session provenance.
2. Market, candle, ticker, account, and holding refreshes update factual snapshots.
3. Normalized holdings remain aligned with Managed Pool, SellEvaluation, and initial position targets.
4. Candidate, rotation, portfolio, constraints, and valuation context feed initial and repeated AI decisions.
5. Validated AI decisions register runtime state, invalidation watches, and effective ETA.
6. Actionable decisions enter RiskGuard and LivePreflight before the existing execution path.
7. A submitted result enters trade-log reflection, holdings refresh, position refresh, and target-set reconciliation.
8. Post-order coordination requests portfolio replanning and remaining-position reconsideration through existing registered AI states.
9. New decisions register fresh ETA state and append local training evidence.
10. LIVE LOG and status evidence explain the decision, data quality, guard result, and next monitoring step in Korean.

## 3. Target Consistency

`normalized holdings` is the position target source. Managed Pool recovery protects actual manageable holdings while excluding dust and non-holdings. The same target set feeds SellEvaluation and initial position decisions. Candidate promotion and rotation remain separate AI-gated paths.

## 4. Decision Cycle

Initial position and portfolio decisions use the shared payload builders. Position and portfolio reconsideration reuse those builders and add prior decision, ETA, invalidation, trigger, and delta context. Provider responses pass validation before runtime registration. A missing or blocked decision does not create an action.

## 5. Guarded Execution

SellUnitGuard validates quantity, current price, selected valuation, and PnL eligibility. RiskGuard and LivePreflight remain mandatory final checks. This Sprint does not change adapter, service, bridge, or router submission behavior. A guard rejection is recorded as a reason, not rewritten into another AI action.

## 6. Post-Order Replanning

The existing successful-submit reflection hook now coordinates the rest of the cycle:

- refresh account holdings and Investment Center positions;
- rebuild normalized holdings and reconcile managed and sell-evaluation targets;
- request portfolio replanning from the registered `portfolio:PORTFOLIO` state;
- request reconsideration for a registered remaining position state;
- run the existing AI scheduler and register the resulting ETA;
- append execution-linked outcome evidence;
- show a Korean explanation of the post-order replanning step.

If a required registered AI state is absent, the coordinator records an incomplete-cycle blocker. It does not invent a decision or state.

## 7. Training Outcome Skeleton

Decision records preserve decision ID, provider, canonical task and scope, action, confidence, reason, ETA, execution result, and after-state placeholders. A submitted order also appends `live_cycle_outcomes.jsonl` with `position_after`, `portfolio_after`, 5-minute, 15-minute, 1-hour, and final outcome checkpoints. Pending checkpoints remain null until a later outcome evaluator owns them.

## 8. Reason Timeline

`LiveCycleReasonTimeline` emits safe Korean summaries for initial decisions, repeated decisions, guard blocks, actual execution reflection, and post-order replanning. `StatusVisibility` records the same display candidate without raw request bodies, account bodies, or provider secrets.

## 9. Completion Harness

`live-operating-cycle-v1-completion-summary --observe-only` combines target PID/session runtime evidence with source-path readiness. It reports Runtime, Data/Targets, AI, Safety, Execution/Replanning, Training, UI, Orders, and a single blocker group. Actual submissions are cross-checked with post-submit reconciliation; no submission is inferred or generated by the harness.

## 10. V1 Boundary

V1 closes the operational structure and outcome linkage. Automated performance scoring and local-first inference/cost policy remain the recommended next Sprint. Those later capabilities must consume the completed training and outcome contract rather than create a parallel operating path.
